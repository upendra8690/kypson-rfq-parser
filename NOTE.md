# NOTE: RFQ parser

**Approach.** Fixed rules, no ML, no network. `parse_rfq` cleans the text ("65gsm" → "65 gsm", ₹, µ) and fixes product typos by edit distance. It then reads every number expression (1,50,000 · 2.5 lac · 15K · 40 hazaar · dedh lakh · fifty thousand) and labels it from the words around it: GSM, micron, size, ply, price, pincode/phone, weight or count. A weight next to a container word or "capacity / SWL / wala", or small enough to be one item's fill (≤75 kg for a BOPP bag, ≤3 t for an FIBC), is a fill weight, not the order. Quantity is picked in this order: number after "qty" > count with a unit > order weight > largest bare number. Category comes from weighted keywords, where specific phrases ("AD star", "jumbo", "duplex") beat generic ones ("bag", "box"). Location comes from the GeoNames gazetteer (about 6,500 Indian towns with alternate spellings, plus world cities, countries and states), scored by cues like "deliver to", "… mein" or a trailing ", City". If nothing matches, it falls back to a capitalised word or a typo match against big Indian cities.

**Score.** `my_tests.jsonl` (64 messages): **64/64 on all six fields**, using Kypson's `score.py`. Also `heldout_tests.jsonl` (62, different style and places): 62/62 with the same scorer. `stress_test.py` (15,000 random messages across 3 seeds, 669 towns not in my tests, scored by its own checker): 14,996/15,000. The labels were written with AI help, so expect lower on your set.

**Three messages it gets wrong** (`known_failures.jsonl`)
1. `20 bundles of 500 bags woven sacks Rajkot` → quantity 20, not 10,000. It takes the first count and doesn't multiply packing units.
2. `need 10000 boxes and 5000 pouches, Pune` → category `pouch` (stronger keyword) with the boxes' quantity. The output holds one product, so multi-product RFQs would need splitting first.
3. `10 lac woven bags 50 kg chahiye UP mein` → location `None`. State abbreviations (UP, MP) are skipped because "up"/"mp" are ordinary words.

**With 1,000 real labelled examples.** Run the parser on them and sort the errors by field, so I fix the rules that fail on real buyers instead of guessing. Fit the thresholds (fill ceilings, location scores) on a training split and keep a fixed test split. Pull new product names, local spellings and typos from the data. Then train a small tagger (CRF or DistilBERT-sized) for each number's role and the location span, with the rules as features and fallback. It replaces a rule only where it scores better on the test split.

**Knowing it works in production.** Log every parse with the rule that set each field and a low-confidence flag (e.g. quantity from a bare number). Track daily the `None` rate per field, the fallback rate and the share of unknown words (a sign of drift). Hand-label 50 random messages a week plus all low-confidence ones. Watch product signals: ops or buyers correcting a field, and suppliers rejecting matches over quantity or location. Every corrected message joins a regression set that must pass before a rule change ships.

**Tools.** Python 3, `geonamescache` (GeoNames data, MIT); `wordfreq` offline only, to list place names that are also English words.
